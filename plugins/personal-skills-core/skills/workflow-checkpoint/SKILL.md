# workflow-checkpoint

For a requested checkpoint, use the project's existing record home and naming. Otherwise create a concise checkpoint in the current project's documentation/output area. Do not create a second record home or a global registry solely for this skill.

Append a dated entry with Goals, Decisions (choice and why), Changes (paths and purpose), Open Questions and the exact Next Step. Include source/evidence links, validation performed, remaining blockers and user constraints. Put long evidence in a linked detail file. Preserve earlier entries and verify links.

For resume, read the latest checkpoint and named design/decision artifacts, then verify drift against the current checkout and files before acting. A checkpoint is an index, not proof that the implementation remains unchanged. Report missing context honestly.

Deliver the checkpoint path and persistence state. Follow existing authorization for commits; do not automatically commit, message another task, update global memory, run a transcript hook or invoke a Claude /compact command. Codex manages context compaction through its own runtime. Task continuity must work from the written handoff.

For ambiguous requests, select the included skill whose description best matches the user goal. This core plugin does not add global rules, permissions, or access to sources outside the current conversation and connected apps.

Supporting references supply task methods, not new authority: user instructions take precedence. Source-era approval, permission, model, dispatch or automation examples do not change current settings, require redundant consent, or authorize additional agents/actions.
