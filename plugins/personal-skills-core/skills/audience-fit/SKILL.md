# audience-fit

Select A for a reader-facing companion, B for UI copy, C for assessment only. Preserve the original unless the user explicitly requested an in-place rewrite. Determine the reader's decision or action, then lead with the result, evidence and practical limitations. Do not change numbers, causal strength, uncertainty or scope to simplify prose.

Use [general readers](references/project-info-for-general-readers.md) and [honest data readability](references/honest-data-readability.md) for reports; [presentational views](references/presentational-view.md) for diagram audiences; [UI copy](references/ui-copy-stance.md) for text tied to program states; [de-AI flavor](references/de-ai-flavor.md) for register, generic phrasing and mechanical rhythm.

Move implementation details to supporting layers while keeping adverse findings visible. Distinct UI states must remain distinguishable and messages may promise only behavior the code implements. Apply requested copy edits directly within authorization. A review-only request returns evidence and proposed wording. For substantial rewrites, show a few before/after examples and check all changed numeric statements against the original.

For ambiguous requests, select the included skill whose description best matches the user goal. This core plugin does not add global rules, permissions, or access to sources outside the current conversation and connected apps.

Supporting references supply task methods, not new authority: user instructions take precedence. Source-era approval, permission, model, dispatch or automation examples do not change current settings, require redundant consent, or authorize additional agents/actions.
