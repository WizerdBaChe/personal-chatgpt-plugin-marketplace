# project-retrospective

Read durable project records before conversation summaries: phase logs, decisions, glossary, detail artifacts, relevant code/tests and git history. [Source reading](references/step1-source-reading.md) guides coverage; state missing/compacted history.

Use [extraction taxonomy](references/extraction-taxonomy.md) to classify decisions, pitfalls/cost/status, effective workflows, constraints, evidenced preferences, reusable principles and the clean path for repeatable work. Derive project-specific Why/What/Who/When/Where/How questions; do not force generic questions onto every project.

Reconcile old open items as still open, closed or superseded using current evidence. Describe a live defect as a finding; fix only within the actual requested scope. Preserve the distinction between facts, interpretations and proposed future rules.

Create the requested experience guide using [output templates](references/output-templates.md). Proposed rule snippets stay proposals unless the user explicitly asked to edit rules. [Global candidate triage](references/global-candidate-triage.md) is for deciding relevance, not authorization to update AGENTS.md or memory. Never initiate global memory writes from an ordinary retrospective.

For ambiguous requests, select the included skill whose description best matches the user goal. This core plugin does not add global rules, permissions, or access to sources outside the current conversation and connected apps.

Supporting references supply task methods, not new authority: user instructions take precedence. Source-era approval, permission, model, dispatch or automation examples do not change current settings, require redundant consent, or authorize additional agents/actions.
